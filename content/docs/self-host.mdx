# Self-hosting Interven

Most customers use the hosted SaaS at `https://api.intervensecurity.com` —
it's the fastest path to production and gets every gateway / telemetry /
ML-sidecar improvement automatically.

Self-hosting is available under an **enterprise license** for environments
that need on-prem deployment, air-gapped operation, or fully-controlled
data residency.

## When self-hosting makes sense

- **Regulated industries** — finance, healthcare, government where every
  byte must stay inside your perimeter
- **Air-gapped deployments** — government or defense customers without
  outbound internet
- **Data-residency requirements** — your tenant's data must physically
  reside in a specific jurisdiction beyond what our SaaS regions support
  today
- **Tight latency budgets** — sub-5ms p50 requirements for ultra-high-RPS
  pipelines that need the gateway co-located with your application

For all other cases, the SaaS is faster to adopt, gets continuous
updates, and handles operations (backups, scaling, ML-model updates,
threat-intel feeds) for you.

## What you get with a self-hosted license

- Full gateway, telemetry, console, and ML-sidecar binaries
- Production-grade docker-compose and Kubernetes manifests
- Per-version migration scripts + rollback procedures
- Encryption-key management runbooks
- Mini-PC / DR cluster backup tooling
- Priority security-advisory feed
- Direct Slack channel with the Interven team

## Requirements

A typical self-hosted footprint:

- **1× Postgres 17** (with the pgvector extension) — sized per traffic;
  hosted services like Neon, RDS, or Supabase work fine
- **1× small VPS** (2 vCPU / 4 GB RAM minimum) for gateway + telemetry + console
- **1× optional ML sidecar** (4 GB RAM, no GPU needed) for B7 semantic-drift
  and prompt-injection-classifier signals
- **Outbound HTTPS** to the threat-intel feed endpoints (or air-gapped
  mirror configuration on request)

Single-VPS deployments run all four services on one Docker host. Multi-node
deployments add a Redis instance for cross-node rate limiting + sticky
session state.

## Required runtime configuration

The full env-var reference (config keys, secrets-generation commands, OIDC
provider setup, alert subscription wiring, retention policy tuning) lives
in the deployment runbook you receive with the license. Highlights:

| Var | Purpose |
|-----|---------|
| `DATABASE_URL` | Postgres connection string (pgvector required for B7) |
| `AIF_CONSOLE_SECRET` | 32+ char hex, JWT signing key |
| `INTERVEN_CREDENTIAL_ENCRYPTION_KEY` | 64-char hex; encrypts tool credentials at rest |
| `INTERVEN_INTERNAL_SECRET` | Service-to-service auth |
| `INTERVEN_API_KEYS_ADMIN_SECRET` | Bearer for the admin `/v1/keys` endpoint |
| OIDC vars | Google + Microsoft SSO providers (optional) |

The credential encryption key MUST be backed up separately from the
database — without it, restored credentials are unrecoverable. The
runbook walks through 1Password / hardware-token procedures.
